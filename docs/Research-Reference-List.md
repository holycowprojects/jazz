## 0. Concrete gotchas found (31 Aug 2026 second research pass) — read before Task 1

These are operational findings, not just references — things that would likely have cost real debugging time if discovered mid-build instead of now.

- **WHPX cannot render an OVMF/UEFI graphical framebuffer on this host at all — confirmed 2 Sept 2026, broader than the originally-documented pflash bug.** The standard `-drive if=pflash,format=raw,file=OVMF_CODE.fd` invocation fails under `-accel whpx` with `WHPX: Failed to emulate MMIO access` — a long-standing QEMU bug ([#513](https://gitlab.com/qemu-project/qemu/-/issues/513)), and the documented fix is `-bios OVMF_CODE.fd` instead of the pflash syntax. **That fix alone was not sufficient on this machine.** Extensive Task 3 testing (many isolation tests: with/without pflash, with/without disks, q35 vs i440fx, a hand-verified-correct monolithic OVMF build sourced from `retrage/edk2-nightly`) found WHPX simply never draws anything to the display under any OVMF/UEFI graphical boot path — the firmware runs correctly (real CPU burn; the exact same firmware rendered the actual UEFI boot-device menu perfectly under `-accel tcg`), WHPX just doesn't display it. **Working fix: bypass firmware graphics entirely.** Use QEMU's direct kernel boot (`-kernel <vmlinuz>`, `-initrd <initramfs>`, `-append "console=ttyS0,115200 ..."`), which boots via SeaBIOS (legacy BIOS) straight into the kernel — no firmware boot menu is ever rendered, so the broken WHPX graphics path is never exercised — with output captured as plain text over a serial console instead of a framebuffer. See `vm/launch-dev-vm.ps1` and `vm/README.md` for the working implementation. **Important consequence:** the live installer environment this boots is BIOS-mode, not UEFI (`/sys/firmware/efi` won't exist in that session) — but SPEC.md requires the *installed target system* to be UEFI (systemd-boot). Task 4/5 must explicitly verify archinstall still produces a correct UEFI target regardless of how the live environment itself booted — don't assume this is automatic.
- **Fix found for the UEFI-target question Task 3 left open — strip the VGA device entirely (2 Sept 2026, Task 4 live testing).** Task 3's direct-kernel-boot workaround (above) sidesteps WHPX's broken OVMF graphics by never invoking firmware graphics at all — but that also means the live environment boots BIOS-mode, so archinstall's bootloader step showed "UEFI is not detected and some options are disabled" and refused to offer `systemd-boot` (only Grub/Limine) — confirming Task 3's carried-over flag was a real blocker, not a non-issue. Root cause, isolated via a standalone test VM: OVMF still had a VGA-capable display device attached even with `-nographic` (that flag only skips opening a window; the device and OVMF's GOP init against it still exist) — so OVMF's console splitter still tried to initialize graphics on the broken WHPX path and stalled before ever producing output, even on serial. **Fix: add `-vga none`** (real OVMF UEFI firmware, `-accel whpx`, `-nographic`, no display device at all). Confirmed working: GRUB's own boot menu and its 10-second countdown rendered correctly over the serial socket — genuine UEFI firmware output, no graphics device for WHPX to fail on. This means a live session booted this way will have a real `/sys/firmware/efi` and archinstall should offer `systemd-boot` normally. **Closed 3 Sept 2026:** getting GRUB to actually boot the archiso's default entry with `console=ttyS0,115200` appended (needed so the *kernel's* output, not just firmware's, reaches serial) — editing the kernel line in GRUB's line editor worked fine (`e`, Ctrl+E to end of line, type the param), but neither Ctrl+X nor F10 (sent as raw bytes/escape sequences over the socket) triggered an actual boot when scripted; F10-as-`\x1b[21~"` was confirmed to be read as bare ESC (cancel) plus stray characters, since GRUB's raw serial input doesn't assemble multi-byte escape sequences into single keypresses the way a real terminal does. **Confirmed fix: a real human keypress (Ctrl+X) through `vm/serial-console-raw.py` worked on the first try**, where scripted byte-injection over the same socket never did — GRUB accepted it immediately and booted straight through to the archiso login prompt with serial output visible throughout. Root cause of the scripted-vs-real difference was never isolated further (not worth the time once the human-keypress path was confirmed reliable).

**Superseded 4 Sept 2026 — the grub.cfg bake-in plan above turned out unnecessary.** Rather than editing the ISO, Task 5 found a simpler combination: **OVMF firmware + QEMU's direct kernel boot (`-kernel`/`-initrd`/`-append`) together, skipping GRUB (and any bootloader) entirely.** QEMU's fw_cfg kernel loader hands the kernel+initrd straight to OVMF, which jumps directly into it — no firmware boot menu is ever drawn, so WHPX's broken OVMF graphics rendering is moot, and no bootloader is ever invoked, so GRUB's un-scriptable raw serial input is moot too. Confirmed directly (not assumed): booted to `archiso login:` fully unattended, then logged in and confirmed `/sys/firmware/efi` was genuinely present (`config_table`, `efivars`, `fw_platform_size`, `runtime`, `runtime-map`, `systab`) — real UEFI, not a fallback. `-vga none` is still required (same reason as the Task 4 finding above — any VGA-capable device stalls OVMF's console splitter even if never rendered to). `vm/launch-dev-vm.ps1` has been updated to this combination (`-bios RELEASEX64_OVMF.fd` + `-vga none` added to the existing direct-kernel-boot args) and its docstring's legacy-BIOS caveat removed. **This same trick turned out to apply to the installed target's own bootloader too:** when Task 5 rebooted the VM from the installed disk (OVMF, no `-cdrom`, no `-kernel`, letting UEFI's boot manager find systemd-boot on the ESP for real), systemd-boot's countdown ("Boot in 2s...") rendered correctly over serial with no keypress needed — the same "no VGA device = OVMF/firmware output goes to serial cleanly" property held for systemd-boot's own menu, not just GRUB's.

**Found 4 Sept 2026 — `snapper rollback` doesn't work on archinstall's default Btrfs layout, and warm reboot crashes OVMF.** Two independent findings from Task 8 (rollback testing):
1. `snapper rollback <num>` fails outright with "Cannot detect ambit since default subvolume is unknown." Cause: archinstall's fstab mounts root by a fixed subvolume *path* (`subvol=/@` — confirmed by reading `/etc/fstab` directly, not assumed), not via btrfs's "default subvolume" mechanism (`btrfs subvolume get-default /` reported plain `ID 5`, never set to `@`'s ID) — which is what snapper's automatic ambit-detection needs. The error's own suggested `--ambit` flag doesn't even exist on this snapper version (0.13.1). This isn't host-specific — it's inherent to archinstall's default layout without `grub-btrfs` (which needs GRUB, not systemd-boot). **Fix: manual recovery instead**, now a reusable script (`scripts/rollback-manual.sh`) — mount the btrfs top-level (`subvolid=5`), rename the current `@` out of the way, snapshot the target restore point in as a new `@`, unmount, cold-boot. Confirmed safe to rename a subvolume while it's the live mounted root (the kernel's mount reference is by subvolume ID, not name) — no rescue-environment boot needed. Works with zero fstab edits specifically because fstab addresses by name (`subvol=/@`), not by ID — checked first, not assumed.
2. Running `reboot` *inside* the guest (as opposed to killing and relaunching the QEMU process externally, which is how every "reboot" elsewhere in this project has actually happened) crashed OVMF with `!!!! X64 Exception Type - 0E(#PF - Page Fault` during the ACPI warm-reset and hung the guest — a new WHPX/OVMF bug, separate from the already-documented graphics-rendering one. The filesystem had cleanly unmounted before the crash (confirmed via the shutdown log), so no data was at risk, but the QEMU process needed a hard `Stop-Process -Force` + fresh relaunch. **Takeaway: never trust in-guest `reboot` on this host — always cold-boot externally** (kill the QEMU process, relaunch fresh). This matters for any future task that needs the guest to reboot.

**Found 4 Sept 2026 — Task 13 completed: numpy 2.4+'s new double-load guard breaks torch 2.14.0's numpy interop, and a verify-script stderr bug masked the real result.** After the disk-space fix below, the rebuilt container still failed its PyTorch check — but for two further, genuinely separate reasons, each found live rather than assumed:
1. **Verify-script bug, not a real failure.** `torch` emits `UserWarning: Failed to initialize NumPy: No module named 'numpy'` (numpy was never actually pinned in `requirements.txt` — torch treats it as optional) but the underlying computation (`torch.zeros(3).sum().item()`) still correctly returned `0.0`. The verify script's `torch_out=$(... 2>&1)` folded that stderr warning into the same string being strict-compared against `"0.0"`, so a functionally-correct run showed as FAIL. **Fix:** added `numpy` as an explicit pinned dependency (a real gap for an AI/Jupyter container regardless) and changed the verify script to redirect stderr to its own file so it can never again corrupt a stdout comparison.
2. **Real version-incompatibility bug.** Pinning `numpy==2.5.2` (latest at the time) then failed differently: `ImportError: cannot load module more than once per process` when torch's `torch.storage` does `import numpy`. Researched via web search rather than guessed: numpy 2.4+ added a stricter guard against its compiled `_multiarray_umath` extension being loaded twice in one process, and torch 2.14.0's internal numpy interop path trips that guard. **Fix: pinned `numpy==2.3.5`** (the last 2.3.x release, confirmed via PyPI, predating the 2.4+ guard) — builds and passes cleanly. Also hit one unrelated transient `pip` `ReadTimeoutError` against `files.pythonhosted.org` mid-diagnosis — a plain retry with no changes fixed it; not a real bug. **Takeaway for any future dependency pin:** a "latest is best" default isn't safe when a fast-moving library (numpy) changes internal enforcement behavior that an unrelated pinned library (torch) hasn't caught up to yet — check for exactly this kind of interaction before assuming a version bump is free.

**Found 4 Sept 2026 (Task 13) — 19GiB is not enough disk for real AI containers; here's how to grow it live.** The base install's Btrfs partition (`~19GiB`, per `install/base-profile.json`'s `disk_config`, itself sized against a 20G disk when Task 4 was run interactively) filled up mid-build: `podman build` for a CUDA-enabled PyTorch + JupyterLab container failed with `no space left on device` (also independently confirmed by a `systemd-journald` "no space left" kernel log line) — even though the `pip install` step itself had *fully succeeded* (`Successfully installed torch-2.14.0 ...`); it was podman's final layer-commit step that ran out of room. `df`/`btrfs filesystem usage /` showed only ~9.2GiB actually available going in — nowhere near enough once torch's unpacked footprint (much larger than its 554MB download) plus the full CUDA 13 toolkit (cuBLAS/cuDNN/cuFFT/cuSPARSE/NCCL/etc.) are accounted for. **Fix, done live without reinstalling anything** (stop VM → `qemu-img resize arch-dev-overlay.qcow2 +60G` on the host → relaunch → inside the guest):
1. `sgdisk -e /dev/vda` (from the `gptfdisk` package) — relocates the GPT backup header to the end of the now-larger disk. **Required first**: without it, `parted ... resizepart` hits an interactive "Fix the GPT to use all the space?" prompt that `parted -s` (script mode) does NOT actually suppress on this system, despite `-s` supposedly meaning non-interactive.
2. `growpart /dev/vda 2` (from the `cloud-guest-utils` package), **not `parted`** — `parted -s ... resizepart 2 100%` *also* hit a second, different interactive prompt ("Partition is being used, are you sure?") that `-s` didn't suppress either, even after the GPT was fixed. `growpart` is purpose-built for exactly this "grow a live, mounted root partition, no prompts" case (it's what cloud images use for first-boot root expansion) and went straight through both times parted got stuck.
3. `btrfs filesystem resize max /` — grows the filesystem to fill the now-larger partition. Confirmed: `df -h /` went from `19G/9.2G avail` to `79G/70G avail`.
**Takeaway for future tasks:** `vm/launch-dev-vm.ps1`'s base-disk creation size was bumped from 20G to 80G for any *new* base disk going forward — but this does NOT fix `install/base-profile.json`'s own `disk_config`, which still hardcodes the ~19GiB partition size from its original Task 4 export. A fresh archinstall run (e.g. re-running Task 6-style reproducibility, or anyone cloning the repo and installing from scratch) will still only get a ~19GiB root partition on a bigger disk unless that JSON is also addressed — flagged here, not yet fixed. Also: expect Task 14 (Ollama model pulls) to potentially hit the same ceiling if run before this is resolved properly at the install-config level, not just patched per-VM.

**Also found 3 Sept 2026 — QEMU disk hotplug doesn't work reliably in the archiso live environment.** Hot-adding a virtio disk to an already-running VM via the QEMU monitor (`drive_add ... if=none,id=drive0` then `device_add virtio-blk-pci,drive=drive0,id=disk0`) succeeds at the QEMU level (`info block` shows it attached), but the archiso kernel never surfaces it as a new block device — archinstall kept reporting "No disks were detected." Restarting the VM with `-drive file=...,if=virtio` present from the start fixed it immediately. **Takeaway: always attach every disk at VM launch time, never rely on hotplug for this ISO.**
- **No TAP networking on Windows QEMU.** User-mode NAT (`-netdev user`) is the practical default. This means `ping`-based host↔guest reachability checks won't work (no ICMP under user-mode NAT) — use an SSH port-forward or similar for any verification script that needs to confirm the guest is reachable.
- **Iterative test-cycle workflow: use qcow2 backing-file overlays, not full reinstalls.** Build the base install once into a backing image, then `qemu-img create -f qcow2 -b base.qcow2 -F qcow2 test.qcow2` per test run; delete/recreate the overlay to reset instantly. Snapshot right after a clean Arch install, before running this project's own scripts.
- **Check `/etc/mkinitcpio.conf`'s `MODULES=()` explicitly during Stage 1** rather than assuming virtio modules are picked up automatically — usually fine via the `autodetect` hook, but occasionally needs a manual addition per community reports.
- **archinstall: Hyprland is a built-in profile**, not something needing a custom one (`archinstall/default_profiles/desktops/hyprland.py` ships in the official repo). Use archinstall's own interactive mode once, choose the Hyprland desktop profile, then use its **"Save configuration" export** as the unattended JSON config — don't hand-author the JSON from scratch, since hand-edited configs are known to crash `--silent` mode. AI tooling (Podman/Python/Ollama) and Quickshell/dotfiles belong in a **separate idempotent bash script layered on afterward**, matching every comparable project researched — not crammed into one custom Python profile, even though archinstall's `custom-commands` option technically supports that.
- **archinstall + Btrfs encryption has known bugs** (encryption sometimes silently not applied, compression requests ignored — [#3975](https://github.com/archlinux/archinstall/issues/3975), [#1031](https://github.com/archlinux/archinstall/issues/1031)). Not relevant now (no encryption in Phase 1 scope) — flag for whenever Stage 7 security hardening picks back up.
- **This exact GPU (Intel Arc 140V, PCI ID `64a0`) is known to fall back to pure software rendering** on some kernels — an Arch forum thread on this specific chip confirms a kernel warning "not officially supported by xe driver in this kernel version." Fix when it matters: boot parameters `xe.force_probe=64a0 i915.force_probe='!64a0'`. **Not relevant to the current QEMU VM work** (no GPU passthrough to the guest) — flag for whenever bare-metal/dual-boot is revisited. Suspend/resume is also a known weak spot on this CPU generation (stuck-at-400MHz-after-resume reports) — same "not blocking now, relevant later" status.
- **Post-install updates: no migrations system needed for v1.** `git pull` + re-run the (already-required-to-be-idempotent) install script, with Snapper's existing auto-snapshot as the rollback safety net, is the honest simplest-thing-that's-safe answer — confirmed by comparing Omarchy's real migrations system (built because raw re-runs can't handle one-time non-idempotent changes) against this project's idempotency requirement, which avoids needing that system in the first place. Add a plain-text CHANGELOG for visibility. Revisit only if a real non-idempotent breaking change actually forces it.
- **Dotfiles: skip chezmoi.** It solves a multi-machine personal-dotfiles problem this project doesn't have. Write configs to reference `$HOME`/XDG variables natively — the pattern every comparable project (Omarchy included) actually uses. Add a **Gitleaks pre-commit hook** (`gitleaks detect --staged`) from the first commit as a cheap, near-zero-maintenance automated backstop, on top of (not instead of) writing configs genericized from the start.

## 0b. Design research findings (31 Aug 2026 third research pass) — read before Stage 5

Reality-checks and concrete architecture recommendations for the desktop/interface layer, against the original blueprint's §6 design vision.

- **Hyprland's "functional animation" vision (§6.4) splits roughly in half.** Workspace-transition and border-color behaviors (trust-domain transitions, red border for offensive VMs) are achievable natively via Hyprland's `windowrule = <action>, match:<property>` syntax (the current form — `windowrulev2` is now deprecated), which re-evaluates live as window properties change; states Hyprland has no native concept of (network status, external-access indication) need a script reacting to Hyprland's own event socket (`.socket2.sock`) and pushing updates via `hyprctl keyword` at runtime — purpose-built wrappers exist (`hyprwatch`, `hyprwhenthen`) rather than hand-rolling raw socket handling. The other half — the GPU-inference pulse, the lab-reset shield transition, network-topology animation — have no window to color at all; these are inherently **Quickshell-side custom widgets**, not Hyprland theming. Scope them as separate QML components from the start.
- **Theming architecture: build a small custom `Theme.qml` singleton, don't adopt Noctalia's or Omarchy's wholesale.** Noctalia's `ThemeService`/Matugen pipeline solves "match my terminal and GTK apps to my wallpaper" — a different problem than this project has. Omarchy's Quattro shell solves "replace 8 separate daemon processes with one plugin-based Quickshell process" — a good architectural idea, but not a theming pattern. The right-sized approach: a `Theme.qml` singleton exposing named state tokens (per-workspace color, trust-domain color, pulse color), driven by QML's standard `Behavior on <property>`, `ColorAnimation`, and `Transition` blocks — ordinary Qt Quick, nothing Quickshell-specific required.
- **Skip dynamic wallpaper-based theming (matugen) for the core design — use it only for non-semantic chrome, if at all.** matugen is the current standard tool for Material-You-style wallpaper color extraction and Quickshell has native support for it, but this project's design principle gives color deliberate *semantic* meaning (red = offensive VM, amber = external network) that only works if color is a designed, reliable signal — not something that drifts with whatever wallpaper is active. Omarchy's own choice validates this: it ships 22 curated static themes as the core experience, with dynamic wallpaper theming as an optional extra, not the default. Build a hand-designed static palette per workspace identity; consider matugen later, only for accent colors that carry no trust-state meaning.
- **Screen-reader compatibility is not currently achievable on Hyprland — reclassify from a goal to aspirational.** Orca (the standard Linux screen reader) depends on AT-SPI2/D-Bus integration that wlroots-based compositors like Hyprland haven't reliably implemented, unlike GNOME/KDE Wayland. The original blueprint's §6.5 phrasing ("screen-reader compatibility *where feasible*") turns out to be doing real, load-bearing work — as of 2026 this isn't feasible on this compositor without upstream changes outside this project's control. Don't plan build time against it.
- **Reduced-motion mostly works, with one real gap:** `animations:enabled = false` in `hyprland.conf` globally disables animations, but trackpad swipe-gesture animations are a confirmed open Hyprland bug that this setting doesn't cover ([hyprwm/Hyprland#3878](https://github.com/hyprwm/Hyprland/issues/3878)). No off-the-shelf desktop-wide `prefers-reduced-motion` signal exists that both GTK/Qt apps and a custom Quickshell shell would automatically share — building that link is project-specific plumbing, not a checkbox.
- **High-contrast/scaling is achievable but is genuinely three separate systems to keep in sync** (GTK, Qt/QML, and XWayland legacy apps each theme independently) — plan real coordination work, not one global toggle.
- **Keyboard-only operation is the strong point, as expected** given Hyprland's tiling-by-design nature — no evidence of Quickshell widgets categorically requiring a mouse, just deliberate keybinding design per widget.
- **AI Command Centre dashboard (§6.3): most of it is buildable now, but the GPU panel specifically is blocked on upstream tooling, not a build task.** `GET http://localhost:11434/api/ps` (Ollama) gives loaded models with VRAM/context/quantization, trivially pollable. `podman stats --no-stream --format json` gives per-container CPU/mem/network cleanly. CPU/memory/temperature/power are standard `/proc`/`/sys` reads (reference `tomgonz/quickshell-simpleperfmeters` for a low-overhead pattern). **But Intel's own GPU tooling doesn't expose VRAM/utilization for Xe-driver GPUs** (confirmed: `intel_gpu_top` explicitly says use `gputop` instead, and even that doesn't expose utilization/memory on Xe) — no confirmed-working tool exists yet for this exact hardware (`xpu-smi` is untested, worth verifying directly before relying on it). Scope the dashboard's v1 to CPU/mem/temp/power + Ollama model list + Podman container status; treat the GPU-utilization panel and the "pulse on active inference" animation as blocked until either `xpu-smi` is verified or GPU work moves to NVIDIA hardware where `nvidia-smi` solves this trivially.
